  Decision Rules

  The logic flows through a priority system: triage first, then layer.

  Phase 1: Triage (what's the minimum viable output?)

  IF time == urgent AND prep_level == zero:
    → ALWAYS produce: pivotal points (max 3-5)
    → The rest depends on medium + stakes

  IF time == urgent AND prep_level > zero:
    → ALWAYS produce: refined pivotal points from existing strategy
    → Focus on gap-filling, not starting from scratch

  IF time >= moderate AND prep_level == zero:
    → ALWAYS produce: strategy brief first
    → Then layer additional components based on medium + stakes

  Phase 2: Layer by situation

  Urgent + High Stakes (the "oh shit" path)
  time <= urgent, stakes >= high, prep_level == zero

    ALWAYS:
      → Pivotal points (3-5 max, ruthlessly prioritized)
      → One-line framing for each point ("lead with X because audience cares about Y")

    IF medium == 1:1 OR medium == group_meeting:
      → Meeting prep doc (printable)
      → Q&A prep session (offer, time-boxed to remaining prep time)
      → Top 3 objections with responses

    IF medium == email OR medium == cold_outreach:
      → Artifact draft (just write the email, no strategy needed)
      → Subject line options

    IF medium == talk:
      → Opening hook + 3 key points + closing CTA (skeleton only)

  Short prep, any stakes
  time == short (hours), any stakes

    ALWAYS:
      → Strategy brief (condensed — 1 page, not 5)
      → Pivotal points

    IF stakes >= high:
      → Objection map
      → Q&A prep session (offer)

    IF medium is synchronous (meeting, talk, call):
      → Meeting prep doc

    IF medium is async (email, doc, proposal):
      → Artifact draft

  Moderate prep, high stakes
  time == moderate (days), stakes >= high

    ALWAYS:
      → Full strategy brief (audience analysis, framing, messaging)
      → Pivotal points
      → Objection map
      → Artifact draft

    IF audience_familiarity <= some_context:
      → Audience research tasks (before generating strategy)

    IF medium is synchronous:
      → Meeting prep doc
      → Rehearsal plan (at least 1 dry run)
      → Q&A prep session

    IF medium == talk OR medium == proposal:
      → Prep plan (day-by-day)
      → Follow-up template

  Extended prep (weeks+)
  time == extended, any stakes

    ALWAYS:
      → Full strategy brief
      → Prep plan with milestones
      → Audience research tasks (even if audience is well_known — always dig deeper)
      → Artifact draft (iterative — first draft early, refine over time)

    IF stakes >= high:
      → Rehearsal plan (multiple sessions)
      → Q&A prep session (multiple rounds)
      → Objection map (comprehensive)
      → Follow-up template

    IF medium == talk:
      → Slide outline / talk structure
      → Timing breakdown per section
      → Transition phrases

  Phase 3: Modifiers

  These adjust any output based on additional context:

  IF audience_receptiveness == hostile OR skeptical:
    → Boost objection map priority (always include, even in urgent)
    → Add "landmines to avoid" section
    → Reframe pivotal points defensively ("acknowledge X, then pivot to Y")

  IF audience_receptiveness == champion:
    → Shift from "convince" to "equip" — give them ammo to advocate for you
    → Add "talking points they can use with others"

  IF subject_familiarity == new_to_me:
    → Add subject research tasks before strategy
    → Flag confidence level in outputs ("this framing assumes X — verify")

  IF prep_level > zero (resuming work):
    → Diff against existing campaign state
    → Only produce components that are missing or need updating
    → Highlight what changed since last session

  User-Defined Deliverable Types

  The built-in types are defaults. Users can define their own in preferences:
  ```
  /things:create-deliverable-type <name> <description> [template]
  ```
  Deliverable types are stored in:
  ~/.things/heres-the-thing/deliverable-types/index.json
  Deliverable types templates are stored in:
  ~/.things/heres-the-thing/deliverable-types/* with the appropriate file extension if relevant to the type.
  Custom deliverable types should support user-defined MCPs and plugins/tools. (e.g., a pdf template, a Google Doc mcp server, etc.)
  ```json
  {
    "custom_deliverable_types": [
      {
        "id": "exec_one_pager",
        "name": "Executive One-Pager",
        "description": "Post-mortem form",
        "template": "post-mortem.pdf",
        "mcp": "executive-one-pager",
        "tools": [Bash("echo 'hello'")]
      }
    ]
  }
  ```
  This necessitates a sort of "custom deliverable" type registry and a "custom deliverable type" agent that knows how to handle them.

  And reference them in goal deliverables like any built-in type.


 What's Missing or Underrepresented

  1. Precedent field — The conversation had precedent: [] as a campaign-level field. The final design has context (free text) but no structured way to reference
  prior campaigns. This was explicitly discussed as an input. The precedent can reference anything as precedent - a prior campaign, an accomplishment, a PR comment, etc.

  2. Subject familiarity dimension — The conversation defined subject_familiarity (new_to_me, familiar, i_built_it, expert) as a modifier that triggers subject research tasks and confidence flags.
   The design doc's decision tree and campaign structure don't capture this anywhere.

  3. Audience research tasks — Listed as an output component in the conversation ("Find out X about Y before proceeding"). The design doc's decision tree doesn't include this as a branch, even
  though the conversation's "moderate prep + low audience familiarity" path produced them.

  4. Champion audience path — The conversation explicitly described: "IF audience_receptiveness == champion → shift from 'convince' to 'equip' — give them ammo to advocate for you." The design
  doc's tree only handles the skeptical/hostile branch.

  5. Resuming work / prep level — The conversation described prep_level (zero, researched, strategized, drafted, rehearsed) and a modifier: "IF prep_level > zero → diff against existing campaign
  state, only produce missing/changed components." This is partially covered by the /prep skill description but the diff behavior isn't specified.

  6. Q&A prep session as interactive practice — Described in the conversation as "plugin plays devil's advocate on your pivotal points." The design doc references it in the time-depth table but
  never defines what it actually is — it's a significant interactive feature (analogous to WDYD mock sessions) that deserves more description.

  7. Conference talk specific outputs — The conversation mentioned "slide outline / talk structure, timing breakdown per section, transition phrases" for extended prep + talk medium. The tree
  simplified away medium-specific branches beyond sync/async.

  8. Custom deliverable agent — The conversation said this needs "a 'custom deliverable type' agent that knows how to handle them." The design doc mentions the concept (line 459) but doesn't
  define it as an actual agent in the plugin architecture (no entry in an agents/ directory or similar).

  9. Tags on outcomes — The outcome structure in the design doc includes tags (line 374), which is good, but the conversation's outcome example also discussed how outcome tags integrate with the
  central tag index. The collection registration for outcomes isn't included — only campaigns and audiences are registered (lines 636-663).

  Minor Inconsistencies

  - /things:create-type is described in Part 2 as a things data layer skill but it should really be owned by `heres-the-thing`.
  - The decision tree branches on "Is delivery synchronous?" and "Is delivery async?" as separate branches (lines 480-494), but these are the same question with opposite answers — the NO branch of
   synchronous IS async. The tree reads like there are three independent checks at the top level when really "synchronous vs async" is one fork. The artifact and/or any user-defined custom type deliverables should be created in the NO branch.
